# 2. SCOPE IMPLEMENTASI

Implementasikan dua user stories berikut.

## US-22 — Halaman Tentang dan Kontak Toko (5 Poin)

### Tujuan

Sebagai pengunjung, saya ingin mengetahui profil toko dan cara menghubungi toko, supaya saya lebih percaya sebelum melakukan pemesanan.

### Acceptance Criteria

1. Ada halaman (misalnya `/tentang`) berisi profil toko, alamat, jam buka, dan kontak. (3 poin)
2. Halaman tertaut dari navigasi atau footer. (2 poin)

### A. Halaman Tentang Toko

Buat halaman publik:

`/tentang`

Halaman ini harus menampilkan informasi toko yang bersumber dari database.

Informasi minimal:

- Nama toko.
- Profil atau deskripsi toko.
- Alamat lengkap.
- Jam operasional.
- Nomor kontak atau WhatsApp.
- Tombol untuk menghubungi toko melalui WhatsApp.

Gunakan data yang tersedia dari pengaturan toko US-43.

Jika data deskripsi profil belum tersedia:

- Periksa apakah sudah ada kolom atau konfigurasi yang dapat digunakan.
- Jika diperlukan, tambahkan field deskripsi toko melalui migration yang aman.
- Jangan membuat informasi pemilik, sejarah, atau identitas toko secara fiktif.
- Jika deskripsi belum diisi, tampilkan informasi yang tersedia tanpa membuat konten palsu.

### B. Informasi Alamat

Tampilkan alamat toko dengan jelas.

Jika alamat tersedia:

- Tampilkan alamat lengkap.
- Sediakan tombol untuk membuka lokasi melalui Google Maps menggunakan alamat tersebut jika memungkinkan.

Jika alamat kosong:

- Jangan membuat tautan peta yang tidak valid.
- Tampilkan informasi bahwa alamat belum tersedia.

Jangan mengarang koordinat atau lokasi toko.

### C. Jam Operasional

Tampilkan jam buka dengan format yang mudah dibaca.

Contoh tampilan:

Senin–Jumat: 08.00–17.00
Sabtu: 08.00–15.00
Minggu: Tutup

Contoh di atas hanya ilustrasi. Gunakan format dan data aktual dari database.

Jika struktur jam operasional saat ini hanya berupa satu field teks, pertahankan kompatibilitasnya dan jangan memaksakan format jadwal harian terstruktur tanpa kebutuhan.

### D. Navigasi

Tambahkan tautan menuju `/tentang` pada navigasi publik atau footer.

Ketentuan:

- Tautan mudah ditemukan.
- Tetap responsif pada mobile dan desktop.
- Jangan mengubah struktur navigasi secara berlebihan.
- Pastikan halaman dapat dibuka langsung melalui URL.

## US-43 — Pengaturan Toko dari Admin (15 Poin)

### Tujuan

Sebagai admin, saya ingin mengubah data toko tanpa mengedit kode, supaya informasi toko mudah diperbarui.

### Acceptance Criteria

1. Halaman admin dapat mengubah nama toko, nomor WhatsApp, jam buka, dan alamat, kemudian menyimpannya ke database. (4 poin)
2. Tombol pesan WhatsApp menggunakan nomor dari pengaturan database, dengan `lib/toko.js` sebagai fallback. (4 poin)
3. Halaman publik (header, footer, dan tentang) menggunakan nama dan jam buka dari database. (4 poin)
4. Nomor WhatsApp divalidasi dan setiap aksi perubahan memeriksa login di server. (3 poin)

### A. Halaman Pengaturan Toko

Buat halaman admin:

`/admin/pengaturan-toko`

Halaman ini hanya dapat diakses oleh admin yang sudah login.

Sediakan form untuk mengelola:

1. Nama toko.
2. Nomor WhatsApp.
3. Jam operasional.
4. Alamat toko.
5. Deskripsi atau profil toko jika diperlukan untuk US-22.

Field utama yang wajib sesuai US-43 adalah nama toko, nomor WhatsApp, jam buka, dan alamat.

Ketentuan:

- Form menampilkan data toko yang tersimpan di database.
- Admin dapat mengubah data.
- Admin dapat menyimpan perubahan.
- Tampilkan feedback ketika penyimpanan berhasil atau gagal.
- Tampilkan loading state ketika proses penyimpanan berlangsung.
- Validasi setiap input sebelum disimpan.
- Data yang sudah tersimpan tetap tampil ketika halaman dibuka kembali.

Gunakan komponen shadcn/ui yang sesuai:

- Input
- Textarea
- Label
- Button
- Card
- Separator
- Sonner atau sistem toast yang sudah tersedia

### B. Database Schema

Periksa terlebih dahulu apakah sudah ada tabel pengaturan toko.

Jika belum tersedia, buat tabel yang sesuai.

Rekomendasi nama tabel:

`pengaturan_toko`

Struktur konseptual:

- `id`
- `nama_toko`
- `nomor_whatsapp`
- `jam_buka`
- `alamat`
- `deskripsi`
- `updated_at`

Pastikan hanya ada satu konfigurasi toko aktif untuk aplikasi ini.

Gunakan salah satu pendekatan:

- Singleton row dengan ID tetap.
- Constraint yang menjamin hanya ada satu konfigurasi toko.

Jangan membuat banyak baris konfigurasi yang menyebabkan data toko menjadi ambigu.

Tambahkan migration SQL yang aman.

Jika tabel sudah tersedia, gunakan schema yang ada dan hindari membuat tabel duplikat.

### C. Pengambilan Data Profil Toko

Buat mekanisme server-side untuk mengambil konfigurasi toko.

Data tersebut digunakan oleh:

- Header publik.
- Footer publik.
- Halaman `/tentang`.
- Tombol WhatsApp.
- Keranjang dan checkout WhatsApp jika sudah diimplementasikan.

Gunakan satu sumber data agar nama toko, nomor WhatsApp, dan jam buka konsisten.

Hindari membuat query database yang sama berulang kali tanpa kebutuhan.

Jika query database gagal:

- Tangani error dengan baik.
- Gunakan fallback yang sesuai untuk informasi yang tersedia.
- Jangan membuat aplikasi crash hanya karena data pengaturan belum tersedia.

Perhatikan caching dan revalidation Next.js agar perubahan pengaturan admin tercermin pada halaman publik setelah disimpan.

### D. Integrasi dengan `lib/toko.js`

Saat ini proyek memiliki konfigurasi toko pada:

`lib/toko.js`

Pertahankan file tersebut sebagai fallback.

Prioritas sumber data:

1. Data pengaturan toko dari database.
2. Nilai fallback dari `lib/toko.js` jika data database belum tersedia atau gagal diambil.

Jangan menghapus `lib/toko.js`.

Buat mekanisme resolver data toko di server jika diperlukan.

Contoh konseptual:

```js
const dataToko = {
  namaToko: dataDatabase?.nama_toko || toko.namaToko,
  nomorWhatsApp: dataDatabase?.nomor_whatsapp || toko.nomorWhatsApp,
  jamBuka: dataDatabase?.jam_buka || toko.jamBuka,
  alamat: dataDatabase?.alamat || toko.alamat,
};
```

Sesuaikan nama properti dengan struktur aktual proyek.

Jangan menyalin contoh ini secara membabi buta.

Pastikan fallback tidak menyebabkan nomor WhatsApp kosong atau URL WhatsApp rusak.

### E. Integrasi Nomor WhatsApp

Semua tombol WhatsApp harus menggunakan nomor dari pengaturan toko database.

Periksa seluruh penggunaan nomor WhatsApp dalam proyek, termasuk:

- Tombol WhatsApp pada halaman detail produk.
- Tombol checkout keranjang.
- Tombol kontak pada halaman tentang.
- Komponen WhatsApp lainnya jika tersedia.

Jangan menyisakan nomor WhatsApp hardcode pada komponen.

Ketentuan:

- Database menjadi sumber utama.
- `lib/toko.js` menjadi fallback.
- Semua komponen menggunakan sumber data yang konsisten.
- Format nomor harus sesuai dengan kebutuhan URL `wa.me`.

Contoh format nomor internasional:

`6281234567890`

Nomor tidak boleh mengandung:

- Tanda `+`.
- Spasi.
- Tanda kurung.
- Tanda hubung.

Pastikan URL WhatsApp tetap menggunakan format:

`https://wa.me/<nomor>?text=<pesan>`

Pesan harus tetap di-encode menggunakan `encodeURIComponent`.

Jangan mengubah format pesan WhatsApp yang sudah berjalan kecuali diperlukan untuk integrasi.

### F. Validasi Nomor WhatsApp

Buat validasi nomor WhatsApp di server.

Ketentuan:

- Nomor wajib diisi.
- Hanya menerima digit setelah normalisasi.
- Hilangkan spasi dan karakter pemisah yang diizinkan.
- Normalisasi awalan nomor Indonesia secara konsisten.
- Nomor harus memiliki panjang yang masuk akal.
- Tolak input yang tidak valid.
- Jangan menerima URL WhatsApp sebagai pengganti nomor telepon.

Jika admin memasukkan nomor dengan format lokal, misalnya `081234567890`, normalisasikan menjadi format internasional `6281234567890`.

Pastikan normalisasi tidak menggandakan kode negara.

Tampilkan pesan validasi yang mudah dimengerti.

### G. Server-side Authentication

Semua operasi perubahan pengaturan toko wajib memeriksa autentikasi admin di server.

Ketentuan:

- Periksa sesi menggunakan mekanisme Supabase Auth yang sudah ada.
- Gunakan `supabase.auth.getUser()` atau pendekatan server-side yang sesuai dengan implementasi proyek.
- Jangan hanya mengandalkan proteksi tampilan atau `proxy.js`.
- Jangan mempercayai status login dari client.
- Validasi seluruh input di server.
- Pastikan pengunjung tanpa login tidak dapat mengubah pengaturan toko.
- RLS tetap aktif.

Jangan menggunakan Supabase secret key untuk melewati otorisasi perubahan data admin yang seharusnya menggunakan sesi admin dan RLS.
