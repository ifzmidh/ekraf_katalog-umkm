# 2. SCOPE IMPLEMENTASI

Implementasikan tiga user stories berikut.

## US-18 — Galeri Beberapa Foto Produk (0/10)

### Kondisi saat ini

- Halaman detail produk hanya mengambil satu kolom `foto_url`.
- Halaman detail hanya menampilkan satu gambar.
- Belum ada thumbnail maupun kontrol untuk mengganti gambar.

### Acceptance Criteria

1. Sistem dapat menyimpan beberapa foto untuk satu produk.
2. Halaman detail menampilkan gambar utama produk.
3. Tersedia thumbnail untuk setiap foto produk.
4. Pengunjung dapat memilih thumbnail untuk mengganti gambar utama.
5. Gambar aktif memiliki indikator visual yang jelas.
6. Galeri responsif untuk perangkat mobile, tablet, dan desktop.
7. Produk tanpa foto tambahan tetap dapat ditampilkan dengan baik.
8. Gambar yang gagal dimuat memiliki fallback.
9. Galeri tetap mempertahankan performa yang baik.
10. Foto produk yang sudah tersimpan sebelumnya tetap dapat digunakan.

### Implementasi Teknis

Periksa terlebih dahulu struktur database yang tersedia.

Jika saat ini hanya terdapat `foto_url`, tentukan strategi penyimpanan beberapa foto yang paling sesuai.

Rekomendasi:

- Buat tabel relasi `produk_foto` jika sesuai dengan arsitektur yang ada.
- Gunakan relasi `produk_id` untuk menghubungkan foto dengan produk.
- Simpan URL foto, urutan gambar, dan timestamp jika diperlukan.
- Pertahankan `foto_url` sebagai kompatibilitas untuk data lama selama masa migrasi.

Contoh struktur konseptual:

`produk_foto`

- id
- produk_id
- foto_url
- urutan
- created_at

Jangan langsung menerapkan struktur tersebut tanpa memeriksa schema aktual.

### UI/UX Galeri

Pada halaman `/produk/[id]`:

- Tampilkan satu gambar utama dengan ukuran proporsional.
- Tampilkan thumbnail di bawah atau di samping gambar utama.
- Thumbnail dapat diklik.
- Gunakan transisi ringan ketika gambar berubah.
- Berikan indikator pada thumbnail yang sedang aktif.
- Pertahankan aspect ratio gambar.
- Hindari layout yang menyebabkan halaman bergeser ketika gambar dimuat.

Gunakan komponen React Client Component hanya pada bagian galeri yang membutuhkan interaksi.

Jika proyek sudah memiliki komponen galeri, prioritaskan reuse daripada membuat komponen baru.

### Integrasi Admin

Periksa form tambah dan edit produk.

Jika admin sudah memiliki fitur pengelolaan foto, kembangkan agar mendukung beberapa foto.

Admin harus dapat:

- Menambahkan beberapa foto.
- Melihat preview foto.
- Mengatur urutan foto.
- Menghapus foto tertentu.
- Menentukan foto utama jika diperlukan.

Gunakan Supabase Storage jika mekanisme upload sudah tersedia atau memang diperlukan.

Jangan mengubah mekanisme penyimpanan foto yang sudah berjalan tanpa alasan teknis yang jelas.

## US-19 — Status Stok (0/5)

### Kondisi saat ini

- Query katalog belum mengambil informasi stok.
- Query detail belum membaca informasi stok.
- Belum ada indikator produk habis.
- Tombol WhatsApp selalu ditampilkan tanpa pengecekan stok.

### Acceptance Criteria

1. Setiap produk memiliki informasi stok.
2. Katalog dapat membaca status stok produk.
3. Halaman detail menampilkan status ketersediaan.
4. Produk dengan stok 0 menampilkan label "Habis".
5. Produk dengan stok lebih dari 0 menampilkan label "Tersedia".
6. Tombol pemesanan WhatsApp tidak dapat digunakan untuk produk yang habis.
7. Produk habis tetap dapat dilihat pengunjung.
8. Tampilan status stok konsisten pada katalog dan halaman detail.
9. Nilai stok tidak boleh negatif.
10. Admin dapat memperbarui jumlah stok melalui form produk.

### Implementasi Database

Periksa tabel `produk`.

Jika belum ada kolom stok, tambahkan kolom yang sesuai.

Rekomendasi:

- `stok INTEGER NOT NULL DEFAULT 0`
- Validasi stok agar tidak bernilai negatif.

Gunakan migration SQL yang aman dan dokumentasikan perubahan schema.

Jangan menghapus atau mereset data produk yang sudah ada.

### Implementasi Query

Pastikan query katalog dan detail mengambil kolom stok.

Tentukan status berdasarkan nilai stok:

- `stok > 0` → Tersedia.
- `stok = 0` → Habis.

Jika data stok lama belum tersedia, gunakan nilai default yang konsisten dan dokumentasikan keputusan migrasinya.

### Implementasi UI

Pada ProductCard:

- Tampilkan badge "Habis" jika stok 0.
- Produk habis tetap bisa dibuka.
- Berikan tampilan visual yang membedakan produk habis tanpa membuat kartu terlihat rusak.

Pada halaman detail:

- Tampilkan status stok dengan jelas.
- Jika stok habis, sembunyikan atau nonaktifkan tombol WhatsApp.
- Tampilkan keterangan seperti "Maaf, produk sedang habis".
- Jika stok tersedia, tombol WhatsApp tetap berfungsi seperti sebelumnya.

Pastikan pengguna tidak bisa melewati pengecekan stok hanya dengan mengubah tampilan di browser. Validasi juga harus dilakukan pada sisi server ketika membuat data atau memproses aksi yang relevan.

Catatan: Karena pemesanan dilakukan melalui WhatsApp, jangan mengklaim stok otomatis berkurang setelah transaksi kecuali memang sudah ada mekanisme pencatatan transaksi.

## US-20 — Harga Coret dan Badge (0/5)

### Kondisi saat ini

- ProductCard dan halaman detail hanya menampilkan `produk.harga`.
- Belum ada harga diskon.
- Belum ada harga normal yang dicoret.
- Belum ada badge "Baru" dan "Terlaris".

### Acceptance Criteria

1. Produk dapat memiliki harga diskon.
2. Harga normal ditampilkan dengan format coret jika diskon aktif.
3. Harga diskon ditampilkan sebagai harga utama.
4. Jika tidak ada diskon, hanya harga normal yang ditampilkan.
5. Sistem menampilkan badge "Baru" berdasarkan data produk.
6. Sistem menampilkan badge "Terlaris" berdasarkan sumber data yang valid.
7. Badge tidak boleh muncul secara acak.
8. Informasi harga konsisten antara katalog dan halaman detail.
9. Harga harus diformat dalam Rupiah.
10. Admin dapat mengelola informasi harga diskon dan status badge melalui mekanisme yang sesuai.

### Implementasi Database

Periksa schema produk terlebih dahulu.

Jika belum tersedia, pertimbangkan penambahan kolom:

- `harga_diskon INTEGER NULL`
- `is_terlaris BOOLEAN NOT NULL DEFAULT FALSE`

Gunakan `created_at` yang sudah ada untuk menentukan status produk baru.

Aturan harga:

- `harga_diskon` bernilai NULL → Tidak ada diskon.
- `harga_diskon` lebih besar dari 0 dan lebih kecil dari `harga` → Diskon aktif.
- `harga_diskon` sama dengan atau lebih besar dari `harga` → Tidak valid.
- Harga tidak boleh bernilai negatif.

Validasi aturan tersebut pada form admin dan server-side.

### Logika Badge "Baru"

Gunakan `created_at` sebagai sumber data.

Rekomendasi:

- Produk yang dibuat dalam 7 hari terakhir mendapatkan badge "Baru".
- Produk di luar periode tersebut tidak mendapatkan badge.

Pastikan perhitungan tanggal menggunakan pendekatan yang konsisten dan tidak menghasilkan perbedaan tidak wajar antara browser dan server.

Jangan menyimpan badge "Baru" sebagai data manual jika statusnya dapat ditentukan dari `created_at`.

### Logika Badge "Terlaris"

Periksa apakah aplikasi sudah memiliki tabel transaksi, detail transaksi, atau sumber data penjualan yang valid.

Jika tersedia:

- Tentukan aturan produk terlaris berdasarkan data penjualan.
- Gunakan periode perhitungan yang jelas.
- Jangan menghitung produk terlaris hanya dari jumlah klik atau kunjungan.

Jika belum tersedia:

- Jangan mengarang data penjualan.
- Gunakan kolom `is_terlaris` sebagai penanda manual yang dikelola admin.
- Dokumentasikan bahwa status "Terlaris" merupakan penetapan manual, bukan hasil perhitungan transaksi.

Jangan membuat sistem transaksi baru dalam scope ini hanya untuk menghasilkan badge terlaris.

### Implementasi UI

Pada ProductCard:

- Harga normal dicoret jika diskon aktif.
- Harga diskon ditampilkan lebih menonjol.
- Badge diskon dapat ditampilkan jika relevan.
- Badge "Baru" ditampilkan berdasarkan `created_at`.
- Badge "Terlaris" ditampilkan berdasarkan sumber data yang valid.

Pada halaman detail:

- Terapkan format harga yang sama dengan ProductCard.
- Pastikan harga normal dan harga diskon tidak tertukar.
- Tampilkan badge yang relevan tanpa membuat layout terlalu padat.

Gunakan formatter Rupiah yang sudah tersedia di project. Jangan membuat formatter duplikat.
